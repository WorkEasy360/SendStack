Authentication

Every request carries your API key as a bearer token.

Authorization: Bearer ss_live_7f3a91c24b8e0d5a91c37e6f2b840195cd7ae3f1
Content-Type: application/json
HTTPS only. The key travels in a header on every request. In production, plaintext HTTP is refused with HTTPS_REQUIRED rather than served — a refusal is the only signal that reaches you before the key has leaked to every hop on the path.

Check a key works before you build against it. /health needs no scope:

curl {{ base_url }}/health \
  -H "Authorization: Bearer $SENDSTACK_API_KEY"
{
  "success": true,
  "api": "online",
  "version": "v1",
  "authenticated": true,
  "workspace": { "id": 12, "name": "Acme Retail" },
  "token": {
    "name": "Production API",
    "key": "ss_live_7f3a91c2\u2026",
    "environment": "live",
    "scopes": ["messages:send", "messages:status"],
    "permissions": ["Send WhatsApp messages", "View message status"]
  }
}

API keys

Create keys in Settings → Developer → API Keys. A key looks like:

ss_live_7f3a91c2 4b8e0d5a91c37e6f2b840195cd7ae3f1
└──┬───┘└───┬──┘ └──────────────┬─────────────────┘
 env    prefix               secret
  • ss_live_ keys send real messages. ss_test_ keys are refused by every send endpoint, so you can point a staging deployment at production and find out by reading a 403.
  • The prefix is stored in clear and shown in the dashboard. Quote it in a support ticket.
  • The secret is stored only as a hash. It is shown once, at creation, and can never be retrieved again. Lost it? Rotate the key.

Rotating issues a new key and revokes the old one immediately, with no grace period — rotation is what you do when you think a key leaked. If you need overlap, create a second key, migrate, then revoke the first.

Scopes

A key holds only the permissions you tick. There is no hierarchy and no wildcard: if an endpoint needs a scope the key does not hold, it answers 403 INSUFFICIENT_PERMISSION and names what is missing.

Rate limits

Three independent buckets, per key. Every response carries the state of the bucket the request charged:

X-RateLimit-Limit: 120
X-RateLimit-Remaining: 118
X-RateLimit-Reset: 1767225660
X-RateLimit-Bucket: requests_per_minute
BucketCharged byProtects
requests_per_minuteevery callthe API tier
messages_per_minutesends, and campaign starts in proportion to their recipientsthe send workers
campaigns_per_daycampaign creation and startsyou, from a loop

Exceeding one returns 429 RATE_LIMITED with Retry-After in seconds. X-RateLimit-Bucket tells you which ceiling you hit — without it, a caller stopped by the message limit sees plenty of request budget left and cannot tell why it was cut off.

Idempotency

Send Idempotency-Key on any POST that causes something irreversible. Retrying with the same key and the same body returns the stored response and sends nothing.

POST {{ base_url }}/messages/send
Idempotency-Key: order-123-confirmation
Authorization: Bearer ss_live_...

A replayed response carries Idempotency-Replayed: true.

SituationResponse
Same key, same body, first request finishedThe stored response, verbatim. Nothing is sent.
Same key, same body, first request still running409 IDEMPOTENCY_IN_PROGRESS. Retry shortly.
Same key, different body409 IDEMPOTENCY_CONFLICT. Use a new key — this is almost always a bug in the caller.
The first request failedThe key is released. Retrying actually runs.

Keys are remembered for 24 hours and are scoped to your workspace.

Health & diagnostics

GET /health

Reachability, plus whether the token you sent is good. Works without a credential, answering "authenticated": false rather than 401, so it doubles as an uptime check. An invalid token is still a 401 — a health check that returns 200 for a revoked key hides the only thing it was asked about.

curl {{ base_url }}/health
{ "success": true, "api": "online", "authenticated": false }

GET /diagnostics

Every link a send depends on, checked and named separately. Use it to tell “my token is wrong” apart from “my WhatsApp number is disconnected” — the two need completely different fixes and a single failure message cannot say which. Sends nothing and reserves nothing. Needs no scope.

Using a template

{
  "to": "919999999999",
  "template_id": "welcome_customer",
  "variables": { "name": "Aman", "order_id": "ORD123" }
}

template_id accepts either the id (tpl_7) or the template's name. Prefer the name: it survives a database restore and reads better in your code.

Marketing vs service

Sends default to "kind": "marketing", which respects the workspace's quiet hours. Pass "kind": "service" for something the customer is waiting on — an OTP, an order update, a reply. Service messages skip quiet hours. Neither ever bypasses an opt-out.

processingBeing handed to WhatsApp now.
sentWhatsApp accepted it.
deliveredIt reached the recipient's device.
readThe recipient opened it.
failedIt will not be delivered. See failure_reason.

Webhooks

Register an endpoint and we push events to it instead of you polling.

curl -X POST {{ base_url }}/webhooks \
  -H "Authorization: Bearer $SENDSTACK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Order service",
    "url": "https://your-app.com/webhooks/sendstack",
    "events": ["message.delivered", "message.failed", "message.received"]
  }'

The response carries the signing secret once. Store it now. Omit events to receive everything.

Each delivery looks like this:

POST https://your-app.com/webhooks/sendstack
X-SendStack-Signature: sha256=8c4f...
X-SendStack-Timestamp: 1767225600
X-SendStack-Event: message.delivered
X-SendStack-Delivery: evt_9c1f4a...

{
  "id": "evt_9c1f4a...",
  "event": "message.delivered",
  "timestamp": "2026-09-03T10:14:09Z",
  "data": {
    "message_id": "msg_918",
    "recipient": "+919999999999",
    "status": "delivered",
    "account_id": 3
  }
}

Delivery guarantees

  • Answer with any 2xx, quickly. Acknowledge first, process asynchronously.
  • Failures retry 5 times with jittered exponential backoff (roughly 10s → 10 minutes).
  • A 4xx other than 408/429 is treated as permanent and is not retried — your URL is wrong, and retrying hides that.
  • Delivery is at-least-once. Deduplicate on id (equivalently X-SendStack-Delivery), which is stable across retries.
  • An endpoint that fails 20 deliveries in a row is disabled, visibly, in the dashboard.

Verifying signatures

Compute HMAC-SHA256 over "{timestamp}.{raw request body}" using your signing secret, and compare in constant time. Use the raw bytes, before any JSON parsing — re-serialising changes them.

import hashlib, hmac, time

def verify(raw_body: bytes, headers, secret: str, tolerance=300) -> bool:
    timestamp = headers.get("X-SendStack-Timestamp", "")
    presented = headers.get("X-SendStack-Signature", "")
    try:
        sent_at = int(timestamp)
    except ValueError:
        return False

    # Replay protection. Without it a captured delivery can be resent forever.
    if abs(time.time() - sent_at) > tolerance:
        return False

    signed = f"{sent_at}.".encode() + raw_body
    expected = "sha256=" + hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, presented)
import crypto from "node:crypto";

export function verify(rawBody, headers, secret, tolerance = 300) {
  const sentAt = Number(headers["x-sendstack-timestamp"]);
  const presented = headers["x-sendstack-signature"] || "";
  if (!Number.isFinite(sentAt)) return false;

  // Replay protection.
  if (Math.abs(Date.now() / 1000 - sentAt) > tolerance) return false;

  const signed = Buffer.concat([Buffer.from(`${sentAt}.`), rawBody]);
  const expected =
    "sha256=" + crypto.createHmac("sha256", secret).update(signed).digest("hex");

  const a = Buffer.from(expected);
  const b = Buffer.from(presented);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

function sendstack_verify(string $rawBody, array $headers, string $secret, int $tolerance = 300): bool
{

using System.Security.Cryptography;
using System.Text;

public static bool Verify(byte[] rawBody, IHeaderDictionary headers, string secret, int tolerance = 300)
{
    if (!long.TryParse(headers["X-SendStack-Timestamp"], out var sentAt)) return false;
    var presented = headers["X-SendStack-Signature"].ToString();

    // Replay protection.
    var now = DateTimeOffset.UtcNow.ToUnixTimeSeconds();
    if (Math.Abs(now - sentAt) > tolerance) return false;

    var prefix = Encoding.UTF8.GetBytes($"{sentAt}.");
    var signed = new byte[prefix.Length + rawBody.Length];
    Buffer.BlockCopy(prefix, 0, signed, 0, prefix.Length);
    Buffer.BlockCopy(rawBody, 0, signed, prefix.Length, rawBody.Length);

    using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secret));
    var expected = "sha256=" + Convert.ToHexString(hmac.ComputeHash(signed)).ToLowerInvariant();

    return CryptographicOperations.FixedTimeEquals(
        Encoding.UTF8.GetBytes(expected), Encoding.UTF8.GetBytes(presented));
}
The timestamp is inside the signature, not merely beside it. If it were only a header, anyone replaying a captured delivery could rewrite it to now and the signature would still verify. Reject anything older than about five minutes.

Inbound messages

When a contact writes to you, you get message.received:

{
  "event": "message.received",
  "data": {
    "message_id": "msg_1204",
    "from": "+919999999999",
    "account_id": 3,
    "type": "text",
    "text": "Hello",
    "contact_id": 88,
    "conversation_id": 12,
    "timestamp": "2026-09-03T10:20:41Z"
  }
}

When they choose one of the options you offered, you get button.clicked instead — never both:

{
  "event": "button.clicked",
  "data": {
    "message_id": "msg_1205",
    "from": "+919999999999",
    "button_id": "interested",
    "button_text": "Interested",
    "interaction_type": "native_button"
  }
}
interaction_type tells you how they chose. WhatsApp reserves tappable buttons for the Cloud API, so on a QR-linked number the options are sent as a numbered list and the customer replies “2”. SendStack resolves that back to the same button_id, so your integration handles both identically — but numbered_fallback vs native_button is there when you want to know.
